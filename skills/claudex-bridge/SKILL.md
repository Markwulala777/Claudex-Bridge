# Claudex Bridge

限定版本的 Linux 双向闭环已实测通过，Windows/macOS 尚未实现并验收。
当前执行入口是 Codex Desktop 与 Claude 原生 TUI；其他原生窗口同步只读查看，
需求输入、权限确认在执行入口完成。安装 Skill 不会自动创建会话或接入全部窗口。
不要因为文件存在、
CLI 已登录、共享历史可读或旧执行器能运行，就宣布完整桥接可用。

## 先检查

用当前 Skill 实际目录运行：

```sh
python3 <skill-directory>/scripts/bridge.py doctor --json
```

`runtime_ready=false` 或退出码 `2` 时，根据 `runtime_blockers` 说明具体缺口并停止本次
派工。不要自动改用 `codex exec`、`claude -p`、新面板、日志或历史导入来替代
用户要求的原生同时显示。不要重启正在工作的客户端或更改其功能门来伪装支持。
诊断不启动模型，也不影响已安装的 `codex-worker`。

本机完整验收通过后可以启用 Linux 开发版；`release_ready` 和
`doctor --require-release` 单独约束三平台验收与 GitHub 发布。不要用本机通过
推断其他平台支持。验收记录必须匹配本机、客户端版本和当前实现，不能手写
“通过”来开启缺失功能。查看器只负责显示；原生适配器执行任务，发起方负责验收。

## 主角色与子代理

- 发起方主 Agent 负责需求、任务书、最终验收和汇报；另一主 Agent 负责实现与测试。
  同一任务不交换主角色。
- Codex 作为执行方时，明确允许它按需委派真正独立的子任务，由主 Codex 汇总、
  验证并负责最终交付。为子任务说明输入、输出和完成标准。
- Claude 子代理默认关闭，以节省额度；用户明确调整时按其选择执行。
- 子代理不得反向唤起另一端或递归调用桥。执行方及其子代理不得批准自己的交付。

## 接入与执行

首次接入或恢复窗口先读 [native-setup.md](references/native-setup.md)。
命令、状态与证据格式见 [workflow.md](references/workflow.md)。只有本机完整验收
通过后才能执行 `task-dispatch`；该命令本身也检查门槛。`task-watch` 只恢复原轮次，
不发送新任务。不要直接调用内部 Python API 绕过未通过的原生接入条件。

用户明确实施后，在授权范围内推进。保存项目、任务书、需求版本、两个主会话
编号、精确执行轮次和每轮验收记录。相同任务返工和反馈继续原会话；独立需求新建。
同时仅有一组主 Agent 执行一个桥接任务。

保留项目已有改动。发起方亲自阅读全部实际改动及必要上下文，核验测试证据。
未通过就给出文件、原因、预期行为与复验标准，回到原执行会话修复。返工后审查
新改动及受影响部分，保持最终交付的完整审查覆盖。不能仅凭执行者总结宣告通过。

默认自动返工，用户可调整上限或停止。同一问题连续两轮没有新证据、修复进展或
可行新方案时停止重复消耗；权限、额度、必须由用户决定的歧义如实报告。
`needs_review` 不等于验收通过；不确定提交、断线、退出或停止请求不等于执行结束。
断线只接回保存的原轮次，不能重发来猜测是否成功。最终汇报完成内容、验收结论、
测试结果及确实存在的遗留问题。自动验收依赖发起方会话仍在运行。

不修改供应商、登录、CC Switch、全局或项目规则。当前复用的 `worker.py` /
`desktop_bridge.py` 只覆盖旧的 Linux Claude → Codex 桌面方向，不能用于宣称
新 Skill 的完整双向能力。新的 `workflow.py` 使用同一状态根和同一 `worker.lock`，
验收绑定需求、执行轮次、最终文件快照及实际测试结果。不要新建状态目录绕过单任务锁。
